# 函数值存储合同保持自反

## 原因

#2045 的 Memof 候选已使用真实 `Map<Fn,MemoEntry>` 存储函数身份与缓存值，
但 Ref 写入会报告期望和实际都是同一个 Map 类型却不兼容。
原合同擦除检查将任意 DynFn 来源都视作信息丢失，也误伤了目标本来就是
DynFn 的位置；目标没有声明具体调用签名，不能假设那里曾有该签名。

## 决策与边界

仅让显式 DynFn 到同类 DynFn 的存储关系保持自反，与明确的开放存储位置
一致。函数值在这里是数据身份，不据此获得调用参数或返回值的证明。
通用递归比较继续覆盖 Ref、Map 及其他嵌套位置，不另造缓存专用规则。

Dynamic 进入具体位置、DynFn 进入具体函数签名、错误 key/value 和不相容
函数签名仍被拒绝。公开签名、函数身份、缓存命中/清理、运行时和后端能力
不变；不增加 Dynamic、unsafe、语言入口、诊断或改写规则。

## 验证方式

在既有 reset! 的 definition :tests 中覆盖函数键的更新、覆盖与删除，
以及显式函数值存储；由现有 reset-proof 回放验证 native/JS 和项目命名空间
的写入检查。现有负例表增加错误键值、开放键、开放函数到具体签名等反例，
不增加 Rust 语义测试或检查脚本。局部 Ref 在 WASM/WASI 上仍明确 unsupported，
固定全局数值 Ref 的原 WASM 正例不受影响。

复制真实 Memof 候选后对照正式 alpha.5 与本地候选：原 once 命名空间检查
14/18，通过修订后为18/18；正常入口 JS 生成及原七项缓存行为测试通过。
没有修改其未提交源码、依赖或质量预算，也不把本地候选测试视作正式配对
发布或整个模块迁移完成。完整回归与审查证据记录在关联 PR。
