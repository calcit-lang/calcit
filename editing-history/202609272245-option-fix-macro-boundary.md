# Option 方法迁移穿过已验证的 core 宏

## 背景

`core-option-method-v1` 即使已证明 `Option<T>` 接收者与目标方法，也把 `assert=`、`do`、`fn` 包裹的调用留给人工审阅。定义测试常把调用放在 `assert=` 内，闭包又常通过 `fn` 表达；这使 Agent 可执行的命名迁移在真实源码中过早停止。

## 决策

只对逐一核实会将原调用单次保留为表达式的 core `do`、`fn`、`assert=` 开放宏边界。原有 `let`、`cond`、`def` 规则不变。宏边界许可并不替代类型证明：接收者仍须静态解析为具体 `Option<T>`，方法契约须指向同一 core helper，源码路径须唯一。`if-not` 等未审计宏、开放类型及函数值仍需人工审阅。

## 验证

Rust CLI 边界测试创建带 schema 与 Calcit `:tests` 的宏包裹定义，检查预览、应用、幂等和执行后的行为；另验证未审计宏不会自动改写。文档解释了此边界，后续以完整仓库检查确认未改变普通编译与 backend 语义。
