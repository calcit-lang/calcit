# `Fn` 的 `(:open …)` 理由与 `W_OPEN_FAMILY` 汇总

方向见 Jon 2026-11-06：生态里 `AnyEnum` / `AnyFn` / `Dynamic` 用得太多，后续要逐步收紧。开放理由只作为 `Fn` 的选项（和 `:generics`、`:features` 同层），不在 snapshot 里加和 `:schema` 平级的字段。

- 写法：`Fn AnyEnum (-> String) (:open :reflect)`，理由只有 `:reflect`、`:decode`、`:host`。`type_expr` 解析 / 打印紧凑写法；规范形式是 Fn map 里的 `:open :reflect`，`VALID_SCHEMA_FIELDS` 与写入校验都认它。
- 存储：`CalcitFnTypeAnnotation.open_reason: FnOpenReasonNote`。`FnOpenReasonNote` 的相等恒为真、`Hash`/`Ord` 不读它，所以带不带 `:open` 的签名是同一个类型，子类型、缓存键不受影响。三个 `to_*_edn` 写出它，Calcit 与 EDN 两条解析路径读回。其余构造处用 `Default::default()`。
- 计数：`snapshot::collect_open_family_count` 遍历项目 namespace（排除内置 core）中写了 `:schema` 的定义，用新增的 `CalcitTypeAnnotation::walk_components` 自顶向下统计 `AnyEnum` / `AnyFn` / `AnyStruct` / `Dynamic`，遇到带 `:open` 的 `Fn` 不再深入。
- 报告：`cr` 加载后算好一行汇总，普通 `--check-only` 在 Notes 之后打印 `Open types: [W_OPEN_FAMILY] …`。它不是 advisory：不改 Notes 计数、不进 JSON 报告、不影响通过与否。先用它观察趋势，库级上限（ratchet）等迁移推进后再加。

验证：`snapshot` 新增 open 理由的紧凑 / EDN / msgpack 往返测试和计数测试；`type_expr` 新增紧凑写法往返与重复 / 未知理由报错测试。
