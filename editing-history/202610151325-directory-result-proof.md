# 目录读取保留真实构造器的返回证据

## 原因

#2048 在 Calcit Paint 0.2.5 暴露：普通检查通过，但严格校验发现 core
`fs-path:read-dir` 的 `Result<List<T>,String>` 中 T 没有输入证据。
宿主实际上使用传入的 StructDef 构造子路径，再使用传入的 EnumDef
返回成功列表或错误字符串；原 proc 的宽参数标记没有表达这个关系。

## 决策与边界

在现有 proc 返回推导中使用真实的定义元数据和通用类型证明关系，
验证单字段 String 构造、成功列表和错误字符串，绑定声明自有的泛型。
保留真实名义身份，不把名字叫作 Result 或 FsPath 当作证据。
不从消费方返回声明反向借用证据；不具备具体定义、字段不匹配、
泛型无法绑定或带未证明 where 约束时，维持原有未证明结果。

类型化 FsPath 参数会在方法加载时触发尚未完成的 trait 附加。
构造器的结构元数据解析因此与既有 Enum 解析对齐：只能从实际数据声明
恢复数据形状和名义身份，不执行未完成的 impl，也不添加方法证据。
这让直接构造后调用与已有 FsPath 参数调用遵守同一合同。

运行时、公开签名、失败语义和后端能力不变。不添加 Dynamic、unsafe、
修复规则、诊断编号或新命令；不自动关闭消费者迁移及正式发布门槛。

## 验证方式

目录成功与缺失行为写在现有 fs:path 的 definition :tests，复用真实小型
子文件 fixture；普通方法调用仍是用户接口。既有严格校验 harness 验证
方法、类型化 receiver、直接 intrinsic 和局部定义别名；错误元素类型、
错误错误类型、未知定义及 Number 字段不得借返回声明获得证明。

用正式 alpha.5 与候选 CLI 对比无依赖最小项目及未经修改的 Paint 0.2.5，
区分 core 关系修复与应用仍需迁移的其他边界，不把单项通过宣称整个应用
完成。按既有统一回放和宿主检查验证 native、Node 及明确不支持的后端。
