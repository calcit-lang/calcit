# if 合流保留 Option 证据

- 修复 #1394：`(if c 0 (min xs))` 合流 `Number` 与 `Option<Number>` 时，先前兼容关系两个方向都判定失败，`merge_if_branch_types` 返回 `None`，绑定退化为未类型化，乘法则静默通过，JS 得到 `NaN`。现在合流会保留 schema 级 `Option<T>` 包装：`Option<T>` 与 payload 分支合流时把 payload 重新包回 `Option`，算术实参或 `Number` 返回契约会报告 `W_FN_ARG_TYPE_MISMATCH` 并保留 `.unwrap-or` / `match` 提示。
- 同时修正 `compatible_if_join` 的方向判断：候选分支只有在“另一分支可被当作该分支使用”时才是合法 join。Option 包装刻意不对称（`Number` 可用于 `Option<Number>` 位置，反之不行），原实现检查了错误方向，会在 `Optional`（无 else 的 `if` 结果）场景直接丢掉 Option。修正后 `if c (some x) 0` 之类也会保留 `Optional`。
- `schema_option_payload` 只对 schema 层 `Option<T>`（`TypeRef`）触发补包；内部 `Optional` 走修正后的兼容方向，避免 `defstruct` 等 core macro 因流敏感守卫（`(empty? pairs)` 之后才用 `&list:first`）产生误报。`option_payload` 作为统一取 payload 的 helper 新增，但 `is_option_type` 语义保持不变，避免影响可选参数 arity（`trailing_option_arg_count`）。
- 测试：Rust 单元测试覆盖 `Number`/`Option<Number>` 双向、内部 `Optional`、开放 payload 与不相关 payload 不伪造 Option；预处理器测试 `if_join_preserves_option_payload_for_arithmetic_checks` 断言 `W_FN_ARG_TYPE_MISMATCH`。手测覆盖 min/max、分支顺序、let 绑定、有无 schema 与 `option:unwrap-or` 正常路径。
- 验证：`cargo fmt`、`cargo clippy -- -D warnings`、`cargo test`、`yarn try-core-tests`、`yarn check-strict-default`、`yarn check-core-dynamic-classification`、`yarn try-rs`、`yarn try-js`、`yarn try-wasm`、`docs check-md` 全部通过。文档在 `docs/features/static-analysis.md` 补充合流规则说明。
