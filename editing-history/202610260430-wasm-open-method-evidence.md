# WASM 在已知调用点保留开放参数的实际方法证据

## 问题与选择

函数公开接收 Enum/Struct 家族时，已经展开的 Local 节点只保留家族注解。
调用者虽然传入了已知名义值，WASM 的普通函数调用仍会丢掉其附加实现，
随后按方法名进入内建分支。自定义 `.contains?` 返回 false 的真实例子会变成 true；
公开 `contains?` 的 Bool 结果检查也可能陷阱。

本阶段复用原固定参数调用点特化与闭包内联，不新增公开入口或类型规则：

- 以原敏感调用传播路径发现普通方法依赖，只有实际名义实参比家族参数更精确时才尝试特化。
- 可选特化不进入现有不支持的 recur、递归展开或可变参数路径，保留这些路径原行为。
- 运行时普通方法按原实现表优先级选择，用户后附加实现覆盖前项；源代码显式名义方法的严格歧义策略和显式 trait-origin 规则不变。
- 复用已选中的真实可调用对象。闭合匿名方法通过原内联机制执行，不在后端函数表冻结后新增合成定义；带词法捕获的方法明确拒绝，不能忽略捕获或改用默认实现。
- 后端的局部证据沿 CoreLet 的初始化、遮蔽和末表达式传递。If 只有两个存活分支证据完全相同才保留实例身份；数据 shape 兼容不能证明附加实现一致。
- 方法结果从实际目标的合同取得，不按方法名声明 Bool，也不把 Number 0/1 当成 Bool。
- 原局部类型记录区分数据合同与实际构造/传递证明的附加实现身份；不另建平行证据表。仅有 `Fn -> Nominal` 返回注解不能证明实例携带的是默认实现。
- 对固定参数、返回名义值的已检查函数，沿实际参数和函数体末表达式恢复实现身份，并再次满足原返回合同；遇到递归或无法证明的分支保留数据合同，不伪造身份。调用参数先推断，再进入函数体递归保护，以支持有限的嵌套身份调用。
- 匿名方法内联复用原 specialization stack，仅在展开方法体期间登记真实函数身份。参数里的有限嵌套调用仍正常编译；递归方法体确定性报告原有 unsupported 诊断，不能耗尽编译器栈。

普通检查的 Local 注解优先规则、共享证明关系、运行时数据布局和 f64 ABI 均不变。
没有增加 Dynamic、unsafe、诊断编号、检查器、迁移规则、后端排除或 CI job。

## 验证方式与真实中间失败

所有语言语义回归保留为 definition `:tests`：core 增加十二项公开 Enum 调用、数值边界、
求值顺序、If、let 与词法遮蔽；原 trait fixture 增加十二项实际自定义实现、相反的 impl 顺序、
匿名方法输出、普通函数转发、名义返回合同与有限嵌套调用。原函数体、schema、测试和断言不删除、不改预期。
新增 trait 回放复用现有 impl-origin-portable 标签，进入原 native/WASM CI 组。
另在原 Rust 后端单元测试中验证编译器栈保护的生效阶段和清理；这是内联器内部 invariant，不代替 Calcit 共享语义测试。

通过官方 transaction dry-run、revision 守卫和完整 readback 编辑两个 Snapshot，
并用整体 program-diff 确认原定义不变、没有 schema widening。
同源四后端运行器比较实际输出；另保留 Number 0/1 方法结果执行后拒绝的真实宿主对照，
不能把编译拒绝、零匹配或错误方法产生的陷阱当作结果检查成功。

中间原型曾让默认 recur 调用进入不支持的特化路径，已撤回该改变；
完整 core 及 check-all 也实际暴露了新增副作用测试的 Local 证据缺口。
仅传入普通推断的 scope 不会覆盖已展开 Local 的原注解，故未修改普通检查策略，
改为在后端现有词法绑定路径传递证据。保留原失败记录，后续重新执行完整验证。

初次提交的完整 Cargo 和 check-all 均通过，但自查新增反例仍发现：factory/identity 的名义返回合同会擦除实际附加实现，WASM/WASI 由基线的陷阱变成错误地返回默认 true。
因此先将 PR 标为 Draft，再修复数据合同与实现身份的混淆，并将 factory、identity 和嵌套 identity 补成永久 `:tests`。
CodeRabbit 随后指出匿名方法递归内联缺少保护，已加入上述 body-only 保护，并以真实递归 fixture 验证 native/JS 的原结果与 WASM/WASI 的确定性拒绝，不添加测试排除。

## 本阶段边界

带自定义实现的递归 wrapper 仍可能走原默认分发；不同分支携带不同实现时也不能伪造统一身份。
这些范围继续留在 #2339，不以当前非递归调用点的通过宣称整个问题完成。
完整 strict 仍保留原 source migration 和 FFI review 边界；类型检查通过不等于整个 workflow 零失败。
Struct 的独立验收继续由 #2380 跟踪，发版仍需原 review、CI 和精确 main 门槛。
