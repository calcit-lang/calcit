# 预处理元数据查询推迟执行未完成依赖的初始化器

## 问题与边界

排查 #2298 时发现稳定的冷启动子用例：加载 bundled core，先预处理 `OptionOpsImpl`，再执行原有生成 `get-env` 的运行时宏。预处理可以返回成功，但随后 `Option` 已处于 errored 状态，记录其依赖 `OptionOpsImpl` 尚不可用。开启和关闭宏展开缓存均可复现。

这个子用例不等于已经证明原 CI 中“.unwrap 得到 fn Macro”的错误具有相同根因。原问题继续保留，不能因为子用例通过而宣称全部收尾。

## 处理方式

预处理的取值辅助函数原先直接运行定义，然后将失败转为没有元数据；失败的惰性初始化器却已经写入运行时错误状态。现有名义声明回退能恢复类型形状，但不能撤销这种过早执行。

现在先准备可用的编译结果，再依据既有 compiled dependency graph 判断惰性初始化器能否到达仍在编译的定义。存在这种依赖时暂不执行初始化器，交给已有声明解析路径；依赖完成后正常执行。已有 Ready 值直接复用，函数和宏的构造不按惰性初始化器处理。图遍历只读已有元数据，处理传递依赖和环，不引入额外持久缓存、命令、类型规则或 Option 名称特例。

准备阶段只编译缺失的 cache entry，与原运行时查询的选择一致；不能借元数据查询重新审计已有编译结果。原型曾因此丢失 Map 方法和名义写入的正向证明，必须保留原 concrete-return / nominal-write 回归，修复取值流程而不是修改断言或放宽关系。

不清空真实初始化失败，不自动重试有副作用的失败初始化，不放宽 Dynamic，也不将未完成的方法表伪装成完整证据。最终运行时 Option 必须仍有真实名义身份和可调用的 unwrap 方法。

## 验证方式

原运行时宏回归同时覆盖直接冷加载和先编译实现的顺序，并继续验证编译期环境读取能力的原拒绝边界。依赖图单测覆盖传递边、独立节点、环和不执行初始化器。这些属于无法通过稳定 Calcit 源码入口合理制造的半编译状态，保留在现有 Rust 边界测试中；用户可见的 Option 与方法语义继续由原 definition tests 和 native/JS/WASM/WASI 回放验证。

运行聚焦回归、完整 Rust 测试、格式与 Clippy，以及启用 post-lowering 校验的完整 check-all。发布和合并仍遵循最新 HEAD review、完整 CI 与精确 main 验证门槛。
